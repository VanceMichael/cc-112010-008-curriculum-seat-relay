# 两校课表与录取门户

教务页面只含虚构学生代号。校历给出学周到实际日期的对应关系，表中时间使用北京时间。

使用 Node.js 22.23.4。执行 `npm ci` 后运行 `npm start`，资料源默认监听本机 4173 端口，可用 `PORT` 指定端口。

`GET /east` 和 `GET /west` 是可浏览的资料入口。`GET /ready` 或 `GET /health` 返回当前发布序号和总发布次数。`PUT /replay` 接受 JSON `{"step":1}`，用于在联调时将来源切到指定发布时刻。发布序号从 0 开始。每次发布只列变化的来源，应答沿用上一轮存在且未被替换的地址。收到 404 并不代表之前的历史资料从业务上被撤回。重新启动服务从第 0 次发布开始。

/east 和 /west 使用 HTML 列出校历、课程和调课。课程行的 data-slot 指学校内部编号，data-joint 上的同一个值由联开组确认。/seats 给共用班面向各校的席位分配和合并发布版本，reservedOpenAt 后指定渠道才能申领未用预留。/changes 是教务员计划。/confirmations 可领取门户确认组；组内 rows 为空的状态表示未生效。POST /enroll 接受 version 和有序 changes，其中每条需要列 student、from、to；409 时 门户不会写入任何席位。
转课提交数组按 student 代号升序排列。教学周从各校标出的周一日期开始，data-day 从 1 起数，data-period 是同一日的课节。调课条目只覆盖所指日期、原课节和课程展示号。确认组的 view 表示同步到的界面，effective 才表示已生效。

回条出现 pending 时 request 保留原转课组，尚无生效席位。门户可在下一次发布才给出同组的有效确认。其他独立确认组在目录中继续可查询。

运行 `npm test` 可校验资料源实际应答。样本内容存放在 `samples/`，开发时通过各来源的本地地址进行联调。

## 教务代办工具

`bin/edu.mjs` 在资料源之上做转课核算，只读页面事实，不代替门户提交。先把资料源跑起来（`npm start`），再在另一个终端执行：

```
node bin/edu.mjs check                     # 来源是否可读、沿用了哪些旧资料
node bin/edu.mjs plan                      # 转课计划（谁可办、谁必须整组、谁只能候补）
node bin/edu.mjs plan --students S1,S2     # 只看某几名学生
node bin/edu.mjs handover                  # 交给班主任的可执行课表
node bin/edu.mjs plan --json               # 同一份结果的机器可读版
node bin/edu.mjs submit --group GRP-S1-S2  # 预览整组提交内容（不加 --commit 不会写门户）
```

`--source` 指定资料源地址（默认 `http://127.0.0.1:4173`），`--step N` 在联调时先切到指定发布时刻再读。

### 判断依据

* **校历**：两校各自编学周，但都从页面标出的周一日期起算。所有冲突先把 `data-week`/`data-day` 换算成日期，再按「日期 + 节次」比较；两校展示号不同不影响。
* **调课与补课**：调课条目只覆盖它指出的日期与学校内部编号；找不到原课时按补课处理，只增加当天的课节。`moved-session-overlap`、`joint-desync` 等提示都带具体日期、节次与展示号。
* **联开课**：只有两校页面都明确写出同一个 `data-joint` 才按共用席位处理。只有一校给出、或他校同名列没有该标记时，不能合并，联开班也不会被当作可执行的共用课。
* **席位**：先看本校配额；本校配额用完、班级仍有空位时，空位属于其他学校或未分配预留，借用必须 `reservedOpenAt` 已过且申请渠道等于 `allowedChannel`。未到时间只能作为备选，渠道不符或没有放位记录直接不能办。没有本校配额的学校不能借别校空位。
* **互换与先后**：A 等 B 释放、B 又等 A 释放才是互换，整组必须一起提交，任一不成立时整组保留原课。只有单向依赖时按先后顺序办理：先办释放方，后办等待方，不把整组拦下。同一学生的多条申请始终一起核对（`linked`），不会拆到两组。
* **确认组**：按「学生 + from + to」与申请匹配。`effective` 才表示已生效；`rows` 为空且 `pending` 表示门户还没写出席位。未生效或提交结果未查清的组，同时保留原位和可能已经接收的位置，其他申请不能用这些名额。
* **未同步 ≠ 未生效**：确认组已生效、但 `view` 里缺少某校时，学生本校课表照常排课，另一校标为「未同步」，并附可查回的确认组号。
* **核对**：`revalidate` 会用最新资料重算同一批申请，遇到新调课、新占位或整组消失就列出变化；`splitIndependent` 只拆出仍可独立办理的申请，联动项保留原课。

### 提交与反复核对

提交一律整组进行，数组按 `student` 升序；门户返回 409 时整组不写入任何席位。工具的 `submit` 会先做三件事：

1. 拆组：只把仍可独立办理的申请发出去，必须联动的项保留原课（`splitIndependent`）。
2. 核对：如果门户确认组里已经有这组记录，先按实际记录判断，不重复提交。
3. 留位：提交后读不到回条时按「未查清」处理，这组同时保留原位与目标位，其他申请不能用。

`lib/session.mjs` 的 `connect()` 会把这三步串起来：`refresh()` 读来源出计划与课表，`submit()` 提交并记录未查清的组，`recheckSubmission()` 在门户稍后给出记录时把它们移出待核对名单。

### 交出的课表

`handover` 每名学生一张表，包含：原班必修课节（继续有效）、转课后课节（仅限已生效的确认组）、跨校共用课的订位依据（席位编号、两校展示号、总席位、分校配额、已落位人数、放位时间与渠道）、尚未交接的选修课，以及确认组逐校区的「已同步 / 未同步 / 未生效」状态。
